# Чекліст ручного тестового платежу

Перегляд коду оплати (`api/billing` → `lib/billing/service.js`, `store.js`, `wayforpay.js`, `mono.js`, SQL `apply_payment_*`) — висновки:

| крок | що перевірено | результат |
|---|---|---|
| створення рахунку | лише власник активної компанії; сума й період беруться з плану на сервері (`planFor`), поля клієнта ігноруються; згода з редакцією оферти; ліміт 10 рахунків/год; id платежу = `crypto.randomUUID()` | OK |
| підпис вебхука | mono: ECDSA по сирих байтах + кеш ключа з обмеженим перезапитом; WayForPay: HMAC_MD5, `timingSafeEqual`, перевірка `merchantAccount`; невалідний підпис → 401, нічого не пишеться | OK |
| ідемпотентність | `apply_payment_success` під `FOR UPDATE`: другий вебхук/статус-чек бачить `credited_at` і нічого не змінює; старіша подія (`modified`) ігнорується | OK |
| сума й валюта | `amountOk` (mono: `amount` + `ccy=980`; WayForPay: сума в копійках + `currency`) звіряється з платежем; розбіжність — не зараховуємо | OK; **виправлено**: розбіжність у першому платежі більше не мовчить — подія + один Telegram-алерт («❗ Оплату не зараховано»), раніше сповіщалось лише автосписання |
| paid_until | `greatest(now, paid_until) + 1 міс/1 рік` у SQL одним оператором; повернення зменшує період один раз | OK |
| тіло запиту | **виправлено**: сире тіло вебхука/запиту обмежене 256 КБ (413) — підпис перевіряється вже після читання, а запит без входу | виправлено |
| cron | `Bearer CRON_SECRET`, порівняння за сталий час | OK |

## Ручний тестовий платіж (перед запуском)

Передумови: Vercel env `PAYMENTS_ENABLED=1`, ключі провайдера (тестові), `PUBLIC_BASE_URL`, `CRON_SECRET`, `TELEGRAM_*`; міграції оплати застосовані.

1. Увійти власником тестової компанії без `is_approved`; у кабінеті відкрити «Оплата». Переконатися: видно лише налаштовані провайдери, суми = тариф (250 грн/міс, річний тариф з `lib/billing/plans.js`).
2. Без згоди кнопка оплати відмовляє; зі згодою — редірект на сторінку провайдера. У БД: `payments` — рядок `pending`, `amount_minor` = тариф, запис згоди (kind=payment).
3. Оплатити тестовою карткою. Після повернення (`?billing=return&pid=…`) екран показує «оплачено до …»; у `org_subscriptions.paid_until` = сьогодні + 1 міс; `payments.status='success'`, `credited_at` заповнено; у Telegram — один алерт.
4. **Повтор вебхука:** у кабінеті провайдера надіслати сповіщення ще раз (або повторити `curl` з тим самим підписаним тілом) — `paid_until` не змінюється, алерту немає, у `payment_events` з'являється ще один рядок.
5. **Підроблений вебхук:** `curl -X POST /api/billing/wayforpay-webhook` (або `mono-webhook`) без валідного підпису → 401, жодних змін у БД.
6. **Розбіжна сума** (лише тестове середовище провайдера): платіж на іншу суму → не зараховано, у Telegram «❗ Оплату не зараховано … сума або валюта не збігаються», доступ не змінився.
7. **Повернення коштів** у кабінеті провайдера: статус `reversed`, `paid_until` скорочується на період один раз, алерт «↩️ Повернення».
8. **Rate limit:** 25 запитів поспіль на `/api/billing/summary` без токена за хвилину → після 20-го відповідь 429 `RATE_LIMITED` з `Retry-After`.
9. Прибрати тестові дані: `payments`, `payment_events`, `org_subscriptions` тестової компанії.
