# Режими роботи та ролі організації

## Режими

- `solo` — один активний користувач. Командні елементи інтерфейсу приховані.
- `team` — доступні учасники, запрошення, ролі, автори та фільтр розрахунків.

Перемикання режиму не видаляє розрахунки чи налаштування. Повернутися з `team` у
`solo` можна лише після відключення всіх інших активних учасників.

Старі організації після міграції отримують `solo`, а старі профілі —
`owner + active`.

## Ролі

| Дія | Owner | Manager | Logist |
| --- | :---: | :---: | :---: |
| Перегляд учасників | ✓ | ✓ | ✓ |
| Запрошення manager | ✓ | — | — |
| Запрошення/відключення logist | ✓ | ✓ | — |
| Зміна ролей | ✓ | — | — |
| Режим `solo/team` | ✓ | — | — |
| Реквізити та назва компанії | редагування | перегляд | перегляд |
| Операційні норми | редагування | редагування | перегляд |
| Власні розрахунки | CRUD | CRUD | CRUD |
| Розрахунки колег | CRUD | CRUD | лише перегляд, якщо owner дозволив |

Останнього активного owner не можна понизити або відключити. Статус
`disabled` блокує API та доступ до даних організації, але розрахунки учасника
залишаються в організації.

## Запрошення

1. Owner або manager надсилає запрошення через `/api/team`.
2. Сервер генерує випадковий токен, а в БД зберігає лише SHA-256 hash.
3. Посилання діє 7 днів і прив’язане до email.
4. Прийняття інвайта виконує RPC `accept_org_invite` в одній транзакції.
5. Порожню організацію, автоматично створену під час реєстрації запрошеного
   користувача, видаляємо після перенесення профілю.
6. Акаунт із розрахунками або іншими учасниками в іншій організації не
   переноситься автоматично.

Для вже зареєстрованого email API повертає посилання, яке можна надіслати
вручну. Ліміт першої версії — 20 активних учасників на організацію.

## Налаштування середовища

Серверні функції потребують:

```text
SUPABASE_URL=...
SUPABASE_SERVICE_ROLE_KEY=...
SITE_URL=https://trip-control.com
```

`SITE_URL` використовується як origin для invite redirect. Якщо значення
некоректне, застосовується `https://trip-control.com`.

## Міграція і перевірка

Міграція: `supabase/migrations/20261012114133_org_roles.sql`.

Перед production:

1. створити Supabase preview branch або локальний стек;
2. застосувати всі міграції;
3. запустити `supabase test db`;
4. перевірити RLS під кожною роллю;
5. лише після цього виконати `supabase db push` у погодженому середовищі.

Агент не застосовує цю міграцію до production автоматично.
