# Контроль+

`app.trip-control.com`: увесь функціонал trip-control.com (калькулятор, «Огляд», історія й шаблони, PDF/Excel, Viber/Telegram,
кабінет, компанія, команда, автопарк, тариф, довідка, ролі, курси валют) + CRM-вкладки «Клієнти» і «Звіт план/факт».
Та сама база й ті самі акаунти Supabase. Окремий Vercel-проєкт (Root Directory = `apps/kontrol-plus`).

## Як зроблено (сайт не змінюється)

- `scripts/sync-site.mjs` (prebuild / predev) копіює з кореня репо `index.html`, `assets/**`, `legal/**`, іконки
  у `.site/` байт у байт (у git не потрапляє). Корінь лише читається.
- Збірка (`vite.config.js`) кладе сайт у `dist/` як є; лише `dist/index.html` отримує вставки між `<!--kp:start-->` /
  `<!--kp:end-->` (`scripts/site-html.mjs`): `noindex`, стилі CRM, `/kp-entry.js` (гість одразу бачить вхід, не лендинг),
  модуль `src/site-bridge.js`, маніфест застосунку замість `/site.webmanifest`. Збірка Vite — у `/kp-assets/`.
- `src/site-bridge.js` (точка входу: стилі + `startBridge()` з `src/bridge.js`) додає в навігацію сайту «Клієнти» і
  «Звіт план/факт» (`#/clients…`, `#/report`), бере клієнт Supabase сайту (`supabaseClient`) — другого клієнта немає.
  Гейт: `kp_context().control_plus`, без тарифу — екран тарифу. Старий ключ сесії окремого застосунку `kp-auth`
  прибирається з `localStorage` при першому завантаженні (сесія сайту не чіпається).
- `/api/*` — серверний rewrite Vercel на `https://trip-control.com/api/*`: для браузера той самий origin, CORS не потрібен,
  `Authorization: Bearer` проходить (перевірено локально через проксі `vite preview`: `/api/calculate` з поганим токеном → 401
  «Недійсний токен»). `api/*` не перевіряє Origin/Host.
- Service worker: сайт реєструє `/sw.js` — тут це SW застосунку (`public/sw.js`); sw.js сайту не копіюється.
  `/api`, Supabase, HTML і файли сайту `/assets/**` не кешуються SW.
- CSP сайту (з `'unsafe-inline'`) — лише на сторінках сайту (`/`, `/index.html`, `/legal/*`, `/offer`…), решта — строгий CSP.

### Залежності моста від сайту

Міст не правує код сайту, але спирається на його розмітку й глобальні імена. Якщо щось із цього зникне, `startBridge()`
поверне `false` (вкладок немає, сайт працює як є, одне попередження в консолі), а тест
`the site still has every id / class / global the bridge depends on` (`tests/site.test.mjs`) впаде.

| Що | Де в сайті | Навіщо мосту |
|---|---|---|
| `const supabaseClient` (глобальна лексична змінна) | inline-скрипт ініціалізації Supabase | єдиний клієнт: сесія, `kp_context`, CRM-запити |
| `#tc-nav-panel .tc-studio-nav` | шапка застосунку | сюди додаються `#kp-nav-clients`, `#kp-nav-report` |
| `#main-app` | контейнер застосунку | сюди вставляється `#kp-crm` |
| `#studio-overview` | «Огляд» у `#main-app` | `#kp-crm` стає перед ним (немає — в кінець `#main-app`) |
| `#sticky-top`, `.tc-legal-footer` | діти `#main-app` | лишаються видимими у вкладках CRM, решта дітей ховається |
| `#studio-nav-calc`, `#studio-nav-overview`, клас `.on` | кнопки навігації | знімаємо підсвітку, поки відкрито CRM |
| `body[data-studio-view]` | `setStudioView()` | будь-яка зміна (калькулятор, огляд, логотип, «Історія», закриття кабінету) закриває CRM |
| `body[data-theme]` (`dark`) | `applyTheme()` | темна палітра `crm.css`; повторна синхронізація навігації |
| `#missing-hint`, `#onboard-banner`, `#cab-warning` | підказки над калькулятором | ховаються у вкладках CRM |
| `html[data-entry]`, `html[data-screen]` | перший inline-скрипт `<body>` | `kp-entry.js`: гість бачить вхід, не лендинг |
| `<link rel="manifest" href="/site.webmanifest">`, по одному `</head>` і `</body>` | `index.html` | точки інжекту (`site-html.mjs` падає, якщо їх не рівно по одному) |
| `navigator.serviceWorker.register('/sw.js')` | код сайту | реєструє SW застосунку; сам міст SW не реєструє |

### Відомі наслідки проксі

- **Інвайт-посилання** `api/team.js` будує з `SITE_URL` сервера сайту → ведуть на `trip-control.com/?team_invite=…`, не на app.
  Прийняти інвайт можна там (той самий акаунт), потім працювати в app.
- Повернення з оплати (WayForPay) — теж на `SITE_URL` (trip-control.com).
- Посилання «поділитися» (Viber/Telegram) і `emailRedirectTo` реєстрації беруть `location.origin` → `app.trip-control.com`.
- Ліміт `/api/poi` рахується за `x-forwarded-for`: перевірити на preview, що Vercel передає IP клієнта, а не свій.

## Ручні налаштування власника (не в коді)

1. **Vercel** (проєкт Контроль+): Root Directory = `apps/kontrol-plus`, увімкнено
   «Include files outside the root directory in the Build Step» — інакше `sync-site` падає з поясненням (сайт лежить у корені).
   Env-змінні Supabase більше не потрібні (`VITE_SUPABASE_*` можна прибрати).
2. **Supabase → Auth → URL Configuration**: додати `https://app.trip-control.com/*` у Redirect URLs (підтвердження email,
   скидання пароля з app).
3. **Google Cloud → Maps browser key → HTTP referrers**: додати `https://app.trip-control.com/*` (і preview-домен Vercel
   на час перевірки), інакше карта й маршрути в app не працюють.
4. Сесія per-origin (`localStorage` `sb-qkfqjorzsxcajcneohoy-auth-token`): на app треба увійти окремо.

## Доступ

Усі права — на сервері (RLS і функції БД з міграцій `20261022090000_kontrol_plus_access.sql`,
`20261022091000_kontrol_plus_clients_reports.sql`). Інтерфейс лише ховає кнопки.

| Хто | Клієнти | Привʼязка рейсів | Звіт |
|---|---|---|---|
| Власник org з планом `control_plus` | читає, додає, редагує, архівує, видаляє | будь-які рейси org | усі рейси |
| Логіст | читає, додає, редагує, архівує | лише свої рейси | свої (усі — якщо «логісти бачать усе») |
| Директор (`org_directors`, до 2 на org) | лише читання | — | усі рейси |
| Org без плану, чужа org, anon | нічого | — | `CONTROL_PLUS_REQUIRED` |

План змінює лише service role (`set_org_plan`) або SQL Editor; директорів додає лише service role.
Гарди Контроль+ дивляться на роль сесії (`anon` / `authenticated` — завжди клієнт), а не лише на claim `role`.

### Організація з клієнтами не видаляється (`clients.org_id … ON DELETE RESTRICT`)

Клієнтів не можна втратити каскадом. Наслідок:

- **Прийняття запрошення падає** (`23503`, foreign key violation), якщо стара організація користувача має клієнтів.
  `accept_org_invite` видаляє стару «порожню» організацію, а `org_has_user_data` (існуюча функція, не змінюється)
  клієнтів не рахує. Клієнти бувають лише в організаціях, що мали тариф `control_plus` (зараз або колись).
  Що робити: перенести або видалити клієнтів у старій org (service role / SQL), потім прийняти запрошення ще раз.
- **Пряме видалення такої організації** (`DELETE FROM organizations`, service role / SQL) так само падає з `23503`,
  доки в ній є клієнти.
- **На тарифі `company` усе як раніше**: реєстрація, прийняття запрошення з видаленням старої порожньої org,
  видалення org (рядки `org_directors` / `calculation_clients` видаляються каскадом). Перевіряє
  `supabase/tests/kontrol_plus.sql`.

## Стек

Vite + vanilla JS (без фреймворку) для CRM-вкладок; сайт — як є. У браузері залежностей немає (Supabase JS вантажить сайт з CDN).
Серверні функції `api/gps/*.js` (Vercel) — єдина залежність `@supabase/supabase-js`.

## Локально

```sh
cd apps/kontrol-plus
npm install
npm run dev                     # http://localhost:5174 — сайт + вкладки, /api проксі на trip-control.com
npm test                        # копія сайту без змін, інжект, rewrite, CSP, гейт, SW, валідація
npm run build && npm run preview  # http://localhost:4174 — те, що піде на Vercel
npm run check:scope             # поза apps/kontrol-plus/ немає змін відносно main
npm run check:db                # усі міграції + Контроль+ і GPS на PGlite, supabase/tests/kontrol_plus.sql і gps_integrations.sql
```

На localhost SW не реєструється (код сайту). Карта Google на localhost працює лише якщо ключ дозволяє цей referrer.

## Vercel

- Framework: Vite, Output: `dist`, `vercel.json` цієї теки (rewrites `/api` і юридичних сторінок, заголовки).
- Власні функції — лише GPS: статичні файли `api/gps/connect.js`, `test.js`, `sync-units.js`, `disconnect.js` (спільний
  хендлер `lib/gps/vercel.js`, `maxDuration` 30 с). Саме статичні, не динамічний `[route].js`: реальний файл у `api/` має
  пріоритет над rewrite `/api/:path*`, тож `/api/gps/*` обробляє Контроль+, а решта `/api/*` і далі йде на trip-control.com.
  Перевірка на preview: `POST /api/gps/connect` без JWT → 401 JSON `AUTH_REQUIRED` з `Cache-Control: no-store` (від Контроль+,
  навіть без env); будь-який інший `/api/*` — відповідь сайту.
- Див. «Ручні налаштування власника» вище.

## GPS (Wialon), етап 2a

Вкладка «GPS» (`#/gps`): підключення Wialon, перевірка, список юнітів і привʼязка юнітів до авто автопарку.
Збирача позицій, крону, карти й привʼязки до заявок **ще немає** (етапи 2b / 2c): `gps_positions` порожня,
`fetchPositions` реалізовано й покрито тестами, але ніхто його не викликає.

- **Хто що бачить.** Вкладку бачать усі ролі організації на `control_plus` (тариф «Компанія» — ні). Власник: підключення,
  перевірка, оновлення юнітів, відключення, привʼязка. Директор: картка статусу й таблиця (перегляд). Логіст та інші: лише
  таблиця юнітів і привʼязок (перегляд). Права перевіряє база (RLS, `gps_map_vehicle`) і API, інтерфейс лише ховає кнопки.
- **Схема:** `supabase/migrations/20261024111415_gps_integrations.sql` (`gps_integrations`, `gps_vehicles`, `gps_positions`,
  Vault-функції, `gps_map_vehicle`, `gps_units`, `gps_purge_old`). pgTAP: `supabase/tests/gps_integrations.sql`.
- **API** (`POST /api/gps/connect | test | sync-units | disconnect`, лише власник, `Authorization: Bearer <JWT>`):
  `connect` перевіряє токен у Wialon і лише тоді зберігає його в Supabase Vault (`gps:<integration_id>`); у таблиці —
  лише `token_hint` («…a1b2») і посилання на секрет. Поля підключення й секрет пишуться однією транзакцією (RPC `gps_connect`):
  якщо Vault не прийняв секрет, не змінюється нічого. Не частіше одного `connect` / `test` / `sync-units` на 10 с на організацію.
  `sync-units` оновлює юніти й повертає підказки привʼязки (назва юніта = номер авто); підказки застосовуються лише кнопкою.
- **Токен** ніде не показується й не логується: не повертається API, не пишеться в таблиці, URL, localStorage чи логи.
  **Увага (прод):** токен передається в базу як параметр RPC `gps_connect` / `gps_store_token` (а `gps_read_token` повертає його
  як результат). Тому на проді не повинно бути `log_statement = 'all'` / `'mod'` чи іншого логування тексту й параметрів запитів
  (`log_min_duration_statement` з параметрами, `pgaudit` з параметрами) для ролі `service_role`, інакше токен потрапить у логи Postgres.
- **Wialon Hosting:** лише `hst-api.wialon.com`, `.eu`, `.us`, `.org`.
- **Wialon Local:** адресу вводить клієнт, тож вона проходить захист від SSRF (`lib/gps/safe-host.js`): лише `https://`
  з доменним імʼям (без IP, `localhost`, `.local` / `.internal` / `.lan` / `.home`), порти 443 або 8443; перед кожним
  запитом DNS-резолв, і якщо хоч одна адреса приватна / службова — відмова; зʼєднання йде саме на перевірену адресу;
  без редиректів. Потрібен **дійсний TLS-сертифікат** (самопідписаний не підтримується) і доступність сервера з інтернету.

### Змінні середовища (Vercel, проєкт kontrol-plus)

`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` — лише серверна функція. Без них `/api/gps/*` відповідає 503 «GPS ще не налаштовано».

### Як клієнту отримати токен Wialon

1. У Wialon створити окремого користувача лише з правом **перегляду** потрібних обʼєктів (авто).
2. Увійти цим користувачем за посиланням
   `https://hosting.wialon.com/login.html?client_id=TripControl&access_type=256&activation_time=0&duration=0&lang=uk&flags=0&user=<логін>`
   (для Wialon Local — той самий шлях на адресі свого сервера). `client_id` — довільна назва застосунку.
   За документацією Wialon (help.wialon.com → API → Getting an access token) форма — це `<host>/login.html` на адресі
   вебінтерфейсу Wialon; окремих адрес форми для серверів API `.eu` / `.us` / `.org` документація не наводить. Тому для
   Wialon Hosting посилання одне (`hosting.wialon.com`), а сервер API обирається у формі окремо; якщо клієнт входить у Wialon через
   іншу адресу (наприклад, домен партнера), він відкриває `login.html` на ній. Токен Wialon — 72 символи.
3. Після входу токен — в адресі після `access_token=`. Вставити його у вкладці «GPS» → «Підключити».
4. Ніколи не надсилати токен у чат чи пошту.

### Обмеження 2a

- **Етап 2b ще не реалізовано:** збирач позицій за кроном, статус «немає сигналу 30 хв», збір лише для змаплених юнітів,
  «поточна заявка» авто = прийнятий рейс від його дати на тривалість + 1 день. `next_poll_at` / `lock_until` /
  `consecutive_failures` у схемі — заготовка для нього; `fetchPositions` написано, але ніхто не викликає.
- Ліміт 10 с тримається в базі (`last_checked_at`): невдалий `connect` оновлює лише `last_checked_at` і `last_error_*` наявного
  підключення (хост, статус і токен не змінюються), а для організації без підключення лишає мінімальний слід — рядок `pending`
  без токена (вкладка показує для нього форму підключення). Тож ліміт діє і між інстансами функції; лічильник у памʼяті —
  додатковий. Не захищає лише від гонки двох одночасних запитів у різних інстансах (обидва можуть пройти перевірку).
- Локально (`npm run dev`) `/api` проксіюється на trip-control.com, тож `/api/gps/*` там не працює — лише на Vercel.

## GPS, етап 2c (карта)

Підрозділ «Карта» у вкладці «GPS» (`#/gps`): авто організації на карті OpenStreetMap, список поруч, у кожного авто — поточна
заявка. Бачать усі ролі організації на `control_plus` (власник, директор, логіст, інші); тариф «Компанія» — ні.
Схема БД не змінювалась: використовуються таблиці 2a (`gps_vehicles.last_*`, `gps_positions`, `gps_integrations.lock_until`).

- **Оновлення без крону.** Карта при відкритті кличе `POST /api/gps/positions` (`{ refresh: false }`), кнопка «Оновити» —
  `{ refresh: true }`. Сервер (service_role) звертається до Wialon лише для привʼязаних активних юнітів своєї організації
  (`active = true`, `vehicle_id IS NOT NULL`), зберігає точки в `gps_positions` (без дублів) і `gps_vehicles.last_*` (лише якщо точка
  новіша), а відповідь будує з бази (`lib/gps/map.js` → `readMap`). Без `refresh` звертаємось до Wialon, лише якщо дані старші
  за 60 с (`last_ok_at` або остання точка організації).
- **Ліміт 60 с на організацію.** Перший барʼєр — лічильник у памʼяті інстансу; другий, міжінстансний — атомарний лок
  `UPDATE gps_integrations SET lock_until = now() + 60 s WHERE id = … AND (lock_until IS NULL OR lock_until < now())`.
  Лок зайнятий — це не помилка: віддаємо дані з бази, `refreshed: false` і `next_refresh_at`; лише явний `refresh: true` у вікні
  дає 429 (теж із даними). Помилка Wialon — дані з бази + `refresh_error`; статус підключення як у 2a; лок не знімаємо.
  Підключення у статусі `error` (тимчасовий збій) оновлюється далі, `error_auth` — ні (недійсний токен не перевіряємо автоматично).
- **`gps_integrations.lock_until` зайнятий лімітом карти.** Збирач 2b має отримати **власне** поле для свого локу (окрема
  міграція в 2b) і не перевикористовувати `lock_until`. Коли зʼявиться 2b, він лише наповнюватиме ті самі `gps_positions` /
  `gps_vehicles.last_*`: свіжі дані від крону означатимуть, що карта не звертається до Wialon; `readMap` не змінюється.
- **Поточна заявка** = лише `accepted` (не `done`: виконаний рейс уже не поточний, навіть у вікні; `draft` / `proposed` /
  `rejected` теж ні), `calc_vehicles.vehicle_id` = авто юніта, `calculations.org_id` = своя організація; вікно за
  Europe/Kyiv: `trip_date ≤ сьогодні < trip_date + ceil(trip_days або 1) + 1 доба`. Кілька — найпізніша, що вже почалась,
  решта — «+N». Клієнт — `calculation_clients → clients.name`, інакше `calculations.client_name`.
- **Деталі заявок на карті бачать усі учасники організації** (власник, директор, логіст, інші ролі) для кожного авто своєї
  організації — без правила `kp_trip_visible` і без маскування заявок інших логістів. Межі: лише своя організація (явний
  фільтр `org_id` на сервері), лише поля заявки з відповіді (дата, маршрут, клієнт). Видимість заявок в інших розділах не змінилась.
- «Немає сигналу» — остання точка старша за 30 хв або її немає.
- **Leaflet 1.9.4** (BSD-2-Clause) з npm, збирається Vite в окремий чанк `/kp-assets/leaflet-*.js` / `.css` і вантажиться лише
  при відкритті розділу (`import('leaflet')`); при виході — `map.remove()`. Маркери — `L.divIcon` (HTML/CSS), без PNG і CDN.
- **CSP:** у правилі сторінок сайту (`/`, `/index.html`, юридичні сторінки) до `img-src` додано `https://tile.openstreetmap.org`
  (тайли — це `<img>`, `connect-src` не потрібен). Строгий CSP решти шляхів не змінювався.
- **Тайли OSM:** `https://tile.openstreetmap.org/{z}/{x}/{y}.png`, `maxZoom` 19, видима атрибуція «© OpenStreetMap contributors»
  з посиланням на https://www.openstreetmap.org/copyright. Без префетчу й офлайн-кешу (service worker пропускає чужі origin).
  Політика тайлів OSM (https://operations.osmfoundation.org/policies/tiles/) — для помірного навантаження; для комерційного
  сервісу з багатьма користувачами варто перейти на власний або платний сервер тайлів (зміна однієї константи `OSM_TILES` і CSP).

## Ремонти і склад запчастин, етап 3a

Вкладка «Ремонти» (`#/repairs`, підрозділи `#/repairs/new`, `#/repairs/stock`, `#/repairs/handlers`) — для організацій на
`control_plus`. Міграція `supabase/migrations/20261024150255_repairs_stock.sql` (лише додає таблиці й функції, повторно
застосовується без помилок), тести — `supabase/tests/repairs_stock.sql` (`npm run check:db`). Поки міграцію не застосовано,
`kp_repairs_context()` не існує, і вкладку просто не видно.

### Ролі й права

| Хто | Бачить | Вносить ремонти й приходи | Сторно ремонту | Коригування, відповідальні, запрошення |
| --- | --- | --- | --- | --- |
| Власник, директор | усе в «Ремонтах» | так | будь-коли | так |
| Логіст-відповідальний (`org_repair_handlers.kind = 'logist'`) | усе в «Ремонтах» | так | свій, до 24 год | ні |
| Менеджер з ремонтів (`kind = 'repair_manager'`) | лише «Ремонти» чужої організації | так | свій, до 24 год | ні |
| Інші учасники організації | лише перегляд | ні | ні | ні |

- **Менеджер з ремонтів** — людина поза командою: не займає місця логіста (ліміт 1 owner + 3 logist не змінився), не стає
  учасником організації (`profiles.org_id` / `org_role` не змінюються). Йому відкрито лише таблиці складу й ремонтів через
  `kp_repairs_org_id()`; до заявок, клієнтів, звітів і GPS доступу немає (ці політики не змінювались і на нові функції не
  спираються). Якщо власна організація менеджера не на `control_plus`, у навігації — лише «Ремонти», без екрана тарифу.
- Менеджером **не може бути людина з власним Контроль+** (активний учасник або директор організації на `control_plus`):
  `kp_repairs_org_id()` віддав би їй власну організацію. `accept` і тригер відмовляють з `REPAIR_MANAGER_HAS_OWN_KP` (409),
  запрошення лишається відкритим.
- До **2 менеджерів** на організацію, запрошення, що очікує, теж займає місце (перевіряє тригер під `FOR UPDATE` організації).
- Логіста призначає власник / директор з активних логістів своєї організації (`kp_repair_handler_add`).

### Собівартість і списання

- Рухома середньозважена: прихід `avg = (qty·avg + q·ціна) / (qty + q)`; списання на ремонт — за поточною `avg`, вона не
  змінюється. Суми — `numeric(14,2)`, середня — `numeric(14,4)`, кількість — `numeric(12,3)`. Дати — Europe/Kyiv.
- `kp_repair_post` блокує запчастини (`FOR UPDATE ORDER BY id`) і пише ремонт **усе або нічого**: не вистачає хоч одної
  позиції — `STOCK_INSUFFICIENT` (у `details` — назва), нічого не списано.
- **Сторно замість редагування.** Списання не редагуються: `kp_repair_void` повертає запчастини на склад за собівартістю
  списання (як прихід), ремонт лишається в історії зі статусом «сторновано». Опис робіт / СТО / одометр можна виправити
  (`kp_repair_update`), дату створення й автора — ні. Прихід (`kp_receipt_reverse`) сторнується, лише поки на складі є вся його кількість; інакше — коригування.
- Коригування (`kp_stock_adjust`, лише власник / директор) — з обовʼязковою причиною: плюс — за вказаною ціною (або поточною
  середньою), мінус — за середньою.

### Запрошення менеджера (`POST /api/repairs/invites`)

- Дії `create` / `resend` / `revoke` / `list` — незаблокований власник своєї організації на `control_plus` або директор (організація —
  як у `kp_org_id()`); `accept` / `decline` — залогінений користувач з токеном і **підтвердженою поштою** (інакше 403
  `EMAIL_NOT_CONFIRMED`). Посилання `https://app.trip-control.com/?repair_invite=<токен>` діє 7 днів. Міст одразу прибирає
  параметр з URL (`history.replaceState`); без сесії токен чекає в `localStorage` (`kp_repair_invite`, не довше 7 днів) з підказкою
  «Увійдіть або зареєструйтеся тією поштою…» — після входу (зокрема після підтвердження пошти в іншій вкладці) запрошення
  приймається, а ключ видаляється за будь-якої відповіді сервера.
- Токен `v2.<id>.<HMAC-SHA256>` підписується `KP_INVITE_SIGNING_SECRET` з префіксом домену `repair_manager|` (не збігається з
  запрошеннями сайту). У БД — лише `sha256` токена; порівняння `timingSafeEqual`; токен і пошта не логуються. Будь-який
  невалідний / чужий / прострочений токен — однаковий 404.
- Лист — через Resend, лише якщо задано `RESEND_API_KEY` і `INVITE_FROM_EMAIL`; інакше посилання повертається тому, хто запрошує,
  і показується з кнопкою «Скопіювати посилання». Ліміти — у БД, під блокуванням організації: не більше 10 надсилань
  (create + resend) на годину на організацію (журнал `repair_invite_sends`) і не частіше разу на 60 с для одного запрошення —
  `REPAIR_INVITE_RATE_LIMIT` (429). Лімітер у памʼяті інстансу — лише перший барʼєр.
- Файли сайту (`api/team.js`, `lib/invite-mail.js`, `org_invites`) не змінювались і не імпортуються — патерн скопійовано.

Змінні середовища (Vercel, проєкт kontrol-plus): `KP_INVITE_SIGNING_SECRET` (обовʼязково; рекомендовано ≥ 32 випадкових байти, напр. `openssl rand -base64 48`; без неї —
503 `NOT_CONFIGURED`), за бажанням `RESEND_API_KEY` і `INVITE_FROM_EMAIL`. Плюс наявні `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`.

### Імпорт початкових залишків (CSV)

«Склад → Імпорт CSV»: файл → перевірка (`kp_parts_import(rows, false)`, помилкові рядки червоним, фільтр «Лише помилки») →
«Імпортувати» (`commit = true`, лише якщо помилок 0; одна транзакція, приходи `kind = 'opening'` з `import_batch_id`).
Колонки: Назва, Артикул, Одиниця, Кількість, Ціна за одиницю, Дата, Постачальник, Примітка (порядок будь-який, є аліаси);
розділювач `;` або `,` визначається сам, десяткова кома, дати `DD.MM.YYYY` / `YYYY-MM-DD`, BOM, лапки за RFC 4180.
До 2000 рядків і 1 МБ (сервер теж перевіряє: понад 2000 рядків або понад 2 МБ JSON — `IMPORT_TOO_LARGE`; без тимчасових таблиць). Наявний артикул — прихід до наявної запчастини. Кнопка «Шаблон CSV» дає приклад.

**Чому без .xlsx:** розбір Excel потребує сторонньої бібліотеки (нова npm-залежність і кількасот КБ у бандлі), а в Excel є
«Файл → Зберегти як → CSV UTF-8». Файл `.xlsx` UI відхиляє з цією підказкою.

Звіт витрат на ремонти по авто й періодах, нагадування про ТО за пробігом / датою (одометр з GPS), мінімальні залишки
(`parts.min_qty` уже є) з попередженнями, вкладення (фото, накладні), експорт. ТО і вартість на км зроблено в етапі 3b (нижче).

## ТО і вартість на км, етап 3b

Підрозділи «Ремонтів» `#/repairs/maintenance` («ТО») і `#/repairs/cost` («Вартість на км»), блок «Виконане ТО» у формі
ремонту, бейдж на кнопці «Ремонти». Міграція `supabase/migrations/20261024232246_repairs_maintenance.sql` (адитивна,
повторно застосовується без помилок; застосовувати після 3a), тести — `supabase/tests/repairs_maintenance.sql`
(`npm run check:db`). Права — як у 3a: читають усі з доступом до «Ремонтів» (`kp_repairs_org_id`), пишуть ті, кому
`kp_repairs_can_write` (власник, директор, логіст-відповідальний, менеджер з ремонтів) — лише через функції; без міграції 3b
блок «ТО» у формі ремонту й бейдж просто не зʼявляються.

- **Шаблон ТО** (`maintenance_types`): назва й інтервал у км і/або місяцях. Порожня організація одною кнопкою отримує
  типовий шаблон (`kp_maintenance_seed_defaults`: масло 15 000 км / 12 міс, фільтри 15 000 / 12, колодки 40 000 / 24,
  трансмісія/мости 60 000 / 24, охолоджувальна рідина 100 000 / 24) — це лише редаговані дефолти. Архівування — мʼяке: тип
  зникає зі статусу й вибору в ремонті, історія виконань лишається. **Перевизначення на авто**
  (`vehicle_maintenance_overrides`): порожнє поле — як у шаблоні, «не відстежувати» прибирає тип для авто.
- **Пробіг** — одна функція `kp_vehicle_mileage_at` (клієнтам — `kp_vehicle_mileage`): остання база з `read_on <= дата` +
  км з рейсів після дня бази (`kp_vehicle_trip_km`). Бази (`kp_vehicle_odometer_bases`, єдиний перелік): ручні показання
  (`vehicle_odometer_readings`, `source = 'manual'`) і проведені ремонти цього авто з одометром (дата — `repair_date`);
  сторнований ремонт базою бути перестає, ремонт без одометра — не база. Однакова дата — перемагає пізніше створена база
  (`created_at`, далі id). Без бази — «Вкажіть показник одометра». В історії «Одометр» видно обидва джерела («Вручну» /
  «Ремонт»; від ремонту — лише дата, км і його id). `source = 'gps'` зарезервовано: GPS пізніше підмінить лише
  `kp_vehicle_mileage_at`.
- **Показання не зменшуються** (`kp_odometer_guard`): нове значення — ручне чи одометр ремонту (тригер на `repairs`) — не
  менше за найпізнішу базу з датою `<=` його дати й не більше за найранішу базу з пізнішою датою (вставка «в минуле» між
  показаннями); рівне — можна. Інакше `ODOMETER_DECREASE` — «Показник одометра менший за попередній (N км на ДД.ММ.РРРР)»
  (`src/lib/errors.js`; для наступної бази — «більший за наступний»). Форма «Одометр» перевіряє те саме заздалегідь
  (`odometerConflict`), але джерело істини — база.
- **Км рейсів** (`kp_vehicle_trip_km`, внутрішня — клієнтам не видана; менеджер з ремонтів бачить лише число пробігу).
  Рахуються заявки зі статусом «прийнято» / «виконано», `trip_date` у вікні `(з, по]`, у яких є рядок `calc_vehicles` для
  цього авто (заявка без привʼязки авто не рахується, навіть з одним авто). У збереженому `calculations.results` планових км
  немає (`planLoadedKm` / `planEmptyKm` — у `computeTrip().raw`, у результат не потрапляють), тому план авто рахується як у
  калькуляторі для зрізу авто (`vehicleSlicePayload`): `calc_vehicles.tonnage` і `snapshot.resolved.payloadTons` (інакше
  `inputs.normWeight`); разовий — 1 ходка × `dist`; циклічний — ходок `ceil(тоннаж / вантажність)`, з вантажем `dist ×
  ходки`, порожнім `dist × (ходки − 1)`; кругорейс — частка зворотного вантажу жадібно за порядком авто (як
  `returnCargoShares`). Факт v2 (`trip_actuals.fact_loaded_km + fact_empty_km`, на всю заявку) ділиться між авто пропорційно
  їхньому плану (як `vehicleFactShares`). **Подача** (`podachaDist`) входить у пробіг: у калькуляторі `totalPodachaKm =
  podachaDist × carsCount`, у зрізі одного авто `carsCount = 1` — тобто подача авто = `podachaDist` один раз на заявку (не на
  ходку). Факт v2 подачі не містить, тому:
  - без факту: км авто = план авто (з вантажем + порожній + подача);
  - з фактом: км авто = факт × план_без_подачі авто / Σ план_без_подачі усіх авто заявки + подача авто;
  - Σ план без подачі = 0: км авто = факт / кількість авто + подача авто.

  Частка факту ділиться за плановим пробігом без подачі, а подача додається кожному авто окремо: у факті її немає, і вона
  однакова для всіх авто. `npm run check:db` звіряє SQL-план з `tripFactBasis` з `api/calculate.js` (`loadedKm + emptyKm +
  podachaKm`; сайт лише читається).
- **Виконання ТО** — форма ремонту зберігає ремонт, списання й «Виконане ТО» одним викликом
  `kp_repair_save_with_maintenance` (одна транзакція: викликає `kp_repair_post` / `kp_repair_update` 3a і
  `kp_repair_set_maintenance`; будь-яка помилка — не збережено нічого, склад не списано). `done_on` = дата ремонту,
  `done_km` = одометр ремонту або розрахунковий пробіг на дату ремонту. Зміна дати, одометра чи авто ремонту перераховує їх
  тригером; авто прибрали (видалення авто на сайті ставить `vehicle_id = NULL`) — ТО цього ремонту видаляються (без авто
  вони нічого не означають, а відмова зламала б видалення авто). Останнє виконання — лише обчисленням серед проведених
  ремонтів: сторно нічого не видаляє, відлік повертається до попереднього виконання, а без виконань — до найранішої бази
  (ручної або ремонту). Список ремонтів показує «ТО: …» лише для проведених.
- **Статус «що раніше»** — гірший з вимірів: км (≤ 0 — червоний, ≤ 5000 — жовтий) і час (настав — червоний, ≤ 14 днів —
  жовтий); межі включні; вимір без інтервалу чи без пробігу ігнорується, обидва — «невідомо». Джерело істини — SQL
  (`kp_maintenance_eval`), у `src/lib/maintenance.js` — копія для сортування й тестів. Бейдж: кількість червоних, а без
  них — жовтих; лише в Контроль+, без листів і сповіщень.
- **Вартість на км** (`kp_repair_cost_per_km`): запчастини (списання без сторно) + СТО проведених ремонтів за
  `[з, по]` / км рейсів за той самий період; без км — «немає пробігу». Період — Місяць / Квартал / Рік / Свій (Київ), до 3
  років; експорт CSV.
- Хвости 3a: подвійний `accept` запрошення (старт + `onAuthStateChange`) — один запит; журнал `repair_invite_sends` старший
  за добу прибирається в `kp_repair_invite_reserve`; директор заблокованої організації не має «власного Контроль+».

- **Права.** Читають owner / logist / director своєї організації на control_plus; створюють документи й оплати — owner і
  logist (`kp_can_write`); анулює документ, змінює реквізити, підпис і печатку — лише owner. Менеджер з ремонтів —
  `KP_FORBIDDEN`. Прямих грантів на нові таблиці клієнтам немає (RLS увімкнено) — усе через RPC `kp_*`. DELETE документів,
  рядків і оплат немає взагалі (тригери забороняють і для service_role): лише анулювання (`status = 'cancelled'`,
  `voided_at`). Знімки `seller` / `buyer` і суми після випуску незмінні.
- **Нумерація** — `kp_doc_counters (org, kind, рік doc_date)`: `INSERT … ON CONFLICT DO UPDATE … RETURNING` тримає рядок
  лічильника до кінця транзакції — паралельні створення не дають дублів; помилка відкочує й лічильник. Ручний номер —
  якщо вільний (`DOC_NUMBER_TAKEN`), більший за лічильник зсуває його. Номери анульованих не повертаються. UNIQUE —
  `(org, kind, рік, номер)`, бо нумерація щороку з 1. Префікси — з реквізитів (знімок у документі).
- **Суми — сервер** (`numeric(14,2)`, курс `numeric(12,6)`): рядок = round(к-сть × ціна, 2). ПДВ 20 % — лише якщо компанія
  платник ПДВ: `net` — ПДВ = round(Σ × 0,20, 2), разом = Σ + ПДВ; `gross` — разом = Σ, ПДВ = round(Σ × 20/120, 2).
  Режим — з документа або `default_vat_mode` компанії. Форма лише показує попередній розрахунок (`previewTotals`).
- **Валюта й курс НБУ.** `POST /api/docs/rate` (`api/docs/rate.js` → `lib/docs/rate.js`): лише з дійсним JWT (401), лише
  POST (405), USD / EUR і дата від 2000 року не в майбутньому (400), до НБУ — сервер з таймаутом 5 с (інакше 502),
  `Cache-Control: no-store`, без JWT у логах. Env — ті самі `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (лише перевірка JWT).
  Курс не довірений: `kp_doc_create` перевіряє rate > 0, дату курсу ≤ дати документа і не старше 7 днів; для UAH курс 1.
  Оплати — у валюті документа, без курсових різниць; у документі — курс, дата курсу й еквівалент у гривнях.
- **Рейси для документа** — `kp_doc_trips_for_client`: рейси клієнта (прийнято / виконано, видимі користувачу) ще не в
  активному документі цього типу; ціна — дохід факту (`trip_actuals.revenue > 0`), інакше план (`calculations.revenue`):
  у факті — те, що реально погоджено після рейсу. Один рейс — на одному активному акті й одному активному рахунку
  (частковий UNIQUE, `TRIP_ALREADY_BILLED`); після анулювання — можна знову. Видалення рейсу на сайті лишає рядок документа.
- **Борги** (`kp_client_debts`): активні рахунки на дату (Київ), окремо за валютами; прострочено — `due_date` < дати і
  борг > 0. Строк оплати рахунку — з документа або `doc_date + payment_terms_days` клієнта (5 днів).
- **Storage**: приватний бакет `kp-doc-assets` (PNG / JPEG ≤ 512 КБ) створює міграція; шлях
  `<org_id>/(signature|stamp).(png|jpg)`, читають учасники організації, пишуть лише власники (політики `kp_doc_assets_*`
  лише для цього бакета). Перегляд — `data:` URL; PDF — підпис і печатка лише нашої сторони, якщо завантажені.
  У `check:db` схема `storage` — мінімальна заглушка (у PGlite її немає), у міграції — нічого зайвого.
- **PDF** (`src/lib/pdf-docs.js`): рахунок на оплату й акт надання послуг (реквізити ч. 2 ст. 9 Закону № 996-XIV, договір,
  «Сторони претензій одна до одної не мають», сума прописом — `src/lib/amount-words.js`), кілька сторінок з повтором
  шапки таблиці, водяний знак «АНУЛЬОВАНО». Файл — `Blob` + `<a download>`. **Залежності** (рівно дві, точні версії, MIT):
  `pdf-lib@1.17.1` — генерація PDF у браузері без сервера й без нових доменів; `@pdf-lib/fontkit@1.1.1` — вбудовування TTF
  з кирилицею (стандартні шрифти PDF кирилиці не мають). Шрифт Noto Sans Regular / Bold (OFL, `public/fonts/OFL.txt`).
  PDF-код і сторінки «Документів» — окремі ліниві чанки: основний бандл майже не росте.
- **CSP** `vercel.json` не змінено (без `unsafe-*`, без `blob:` в img-src, без нових доменів); у `functions` додано
  `api/docs/*.js`.
- До застосування міграції вкладка «Документи» схована (перевірка `kp_doc_next_number`), форма клієнта не надсилає нових
  колонок, картка клієнта — без блоку документів.

## PWA / Microsoft Store

`public/manifest.webmanifest` (id, standalone, window-controls-overlay, іконки any + maskable, скриншоти wide/narrow),
`public/sw.js`, `public/offline.html`. Service worker не перехоплює Supabase, інші домени й не-GET; HTML не кешує;
