# «Власний парк» — етап 1

Модуль для однієї організації (агрохолдинг, що возить лише для себе): підрозділи, поля й точки, роль «Замовник підрозділу», внутрішні
заявки на рейс і диспетчерська дошка. Для всіх інших організацій нічого не змінюється: пункту меню й роутів немає, код модуля не
завантажується.

## Як увімкнути (вручну, на проді — лише після рев'ю міграції `20261120090000_own_fleet.sql`)

Прапорець живе в `organizations.features` (jsonb). UI для клієнта немає; змінити його може лише service_role / суперадмін / SQL-редактор
(тригер `protect_org_features` забороняє змінювати `features` будь-кому з користувацьким JWT, зокрема власнику).

```sql
UPDATE public.organizations
SET features = features || '{"own_fleet": true}'::jsonb
WHERE id = '<org uuid>';   -- організація має бути на plan = 'control_plus'
```

Вимкнути — `features = features - 'own_fleet'`: усі таблиці модуля одразу віддають 0 рядків (навіть директору), пункт меню зникає,
`#/own-fleet…` веде на огляд. Дані лишаються.

## Ролі

| Підпис у UI | Ключ | Що бачить у модулі |
|---|---|---|
| Директор | `owner` | усе; підрозділи, точки, запрошення замовників, усі переходи заявок |
| Менеджер | `director` (org_directors) | те саме |
| Логіст | `logist` | те саме |
| Замовник підрозділу | `requester` (org_requesters) | лише «Власний парк → Заявки» свого підрозділу (створити, переглянути, скасувати свою нову); номер авто й ПІБ водія — у призначеній заявці |

`requester` — окрема таблиця членства (як `repair_manager` у 3a), бо `profiles.org_role` має CHECK `(owner, logist)` і спільний із сайтом.
Тому ліміт «1 директор + 3 логісти» на неї не діє; свій ліміт — 30 замовників (разом із відкритими запрошеннями). Призначити роль в
організації без `own_fleet` не можна (тригер `own_fleet_guard_requester`). Замовник не є учасником `kp_org_id()`: клієнти, документи,
авто, водії, налаштування й команда йому закриті (RLS), у меню лишається один пункт.

Запрошення — `POST /api/own-fleet/invites` (`create` / `resend` / `revoke` / `list` / `accept`), з вибором підрозділу; посилання
`?requester_invite=…`. Токен — 32 випадкові байти, у БД лише sha256; пошта для прийняття береться з акаунта (підтверджена).
Env — ті самі, що в запрошень ремонтів: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY` / `INVITE_FROM_EMAIL` (необов'язково).

## Заявки

`new → accepted → assigned → in_progress → done`; `cancelled` з будь-якого до `done` (причина обов'язкова). Переходи — лише RPC
`fleet_request_transition` / `fleet_request_assign` / `fleet_request_create`, журнал `fleet_request_log`. Призначення бере авто, водія
й (за потреби) причіп з наявних довідників; перетин у часі авто чи водія з іншою заявкою (`wanted_at` … `+ duration_h`) — лише
попередження (`fleet_request_conflicts`), не блок.

## Правила, уточнені за рев'ю (міграція `20261121090000_own_fleet_fixes.sql`)

- **Зняти призначення**: `assigned → accepted` (кнопка в картці заявки; директор, менеджер, логіст). Очищає авто, причіп, водія, `assigned_at` і
  звʼязок із подорожнім листом, пише в `fleet_request_log` («Призначення знято: <авто>»). Рейс, що вже почався, зняти не можна.
- **Звʼязок із подорожнім листом**: `trip_id` — це `kp_doc_trip_sheet.id`. `fleet_request_set_trip` перевіряє, що лист існує й належить
  організації користувача (`FLEET_REQUEST_BAD_TRIP`); `NULL` знімає звʼязок. FK немає навмисно — наявний тест відкату міграції подорожніх
  робить `DROP TABLE kp_doc_trip_sheet`.
- **Призначення**: водій — лише активний, причіп — лише активний («Причіп в архіві»). У авто (`fleet_vehicles`, таблиця сайту) стану «архів»
  немає: «Деактивувати» в автопарку видаляє рядок, і таке авто призначити не можна. Колонку на таблиці сайту не додавали.
- **Запрошення замовника**: акаунт, що вже працює в іншій компанії, відхиляється (`REQUESTER_WORKS_ELSEWHERE`, «Цей акаунт уже працює в іншій
  компанії»). «Працює» = активний логіст чужої організації, директор (`org_directors`) чужої організації або учасник чужої організації на
  `control_plus` (власний Контроль+). Власник власної пробної чи «Компанія» організації — не вважається. Правило діє і в тригері на
  `org_requesters`, тож обійти його прямим `INSERT` не можна.
- **Вкладка «Команда» кабінету**: у організації з `own_fleet` директор і менеджер бачать блок «Замовники підрозділів» (список із поштою / ПІБ і
  підрозділами, відкриті запрошення, «Запросити», «Змінити підрозділи», «Прибрати», «Повторити» / «Скасувати» запрошення). Блок вставляє міст
  (`bridge.js`, `fillRequestersBlock`) після картки команди сайту, `index.html` не змінюється. Без прапорця, логісту й замовнику блоку немає.
  Пошту й ПІБ замовників віддає `own_fleet_requesters_list()` (ПІБ — з метаданих акаунта, якщо є; інакше лише пошта).
- **Архівація підрозділу**: членство замовників у ньому не видаляється (дані й історія лишаються), але архівний підрозділ не пропонується у виборі
  при створенні заявки (форма заявки, фільтри дошки, запрошення, «Змінити підрозділи») і сервер не приймає нових заявок на нього
  (`OWN_FLEET_UNIT_NOT_IN_ORG`). Наявні заявки підрозділу, що в архіві, лишаються видимими й обробляються як зазвичай; розархівація повертає все як було.
